HAVOC USERBOT — MASTER ENGINEERING SPECIFICATION

Version 2.0 | 100 Feature Areas | English + Farsi

---

1. PROJECT MISSION

You are an autonomous senior software engineer, Python architect, Telegram API specialist, QA engineer, and technical writer working inside my connected GitHub repository.

Your mission is to build HAVOC, a powerful, modular, intelligent, highly customizable Telegram userbot that operates on my own Telegram account.

HAVOC should feel like a complete personal Telegram operating system rather than a collection of unrelated commands. It should understand context, detect relevant events, automate repetitive tasks, manage information, help me communicate, and adapt to my preferences.

The project must support English and Farsi (Persian) as first-class languages. This applies to commands, help messages, automatic responses, notifications, errors, configuration descriptions, and the user interface presented through Telegram messages.

The goal is a comprehensive, reliable application that can grow over time without requiring a rewrite whenever I want another feature.

Your responsibilities

1. Inspect my connected GitHub repository before making changes.
2. Understand its existing code, dependencies, branches, conventions, and project structure.
3. Preserve useful existing work.
4. Design the architecture and implementation plan.
5. Implement the features directly in the repository.
6. Run tests and fix discovered problems.
7. Document installation, configuration, usage, security, and troubleshooting.
8. Report what actually works and what remains incomplete.

Do not merely give me a plan, generate a giant untested script, or claim that something works without verifying it. Make real progress in the available environment and continue until the implementation is as complete as practical.

- Language: Python 3.11+.
- Telegram library: Telethon, unless the existing repository has a compelling compatible reason to use another MTProto client.
- Storage: SQLite initially, with a clean database abstraction that can support another backend later.
- Asynchronous architecture using asyncio.
- Testing: pytest.
- Configuration through environment variables and a local ".env" file.
- Modular features, reusable utilities, structured logging, and centralized command registration.
- Full English and Farsi support.
- Automatic language, message-type, and event detection where appropriate.
- Reliable persistence across restarts.
- Sensible security defaults and clear error messages.
- No secrets committed to Git.
- Optional AI services must never be mandatory for basic functionality.
- No paid API should be required for core features.
- Never replace working functionality with stubs just to claim a feature is complete.
- Never silently swallow errors that should be reported or investigated.
- Do not overwrite existing repository content blindly.

This is a userbot for my own Telegram account, not merely a Bot API bot. Implement account authentication appropriately and explain the permissions and risks involved.

Do not implement unsolicited mass messaging, spam campaigns, credential theft, session theft, hidden surveillance, or mechanisms intended to evade Telegram's enforcement systems. Respect Telegram's API rules, flood limits, privacy boundaries, and access controls.

3. LANGUAGE AND LOCALIZATION SYSTEM

This is one of the most important requirements.

HAVOC must be bilingual throughout the application, not just translate the help command.

Language requirements

- English ("en").
- Farsi/Persian ("fa").
- Automatic language detection.
- Manual language selection.
- Per-chat language preferences where appropriate.
- Per-feature language preferences.
- User-configurable fallback language.
- Mixed English/Farsi message handling.
- Persian-aware text formatting.
- Proper right-to-left display where supported.
- Language-aware dates, numbers, and notifications.

Language detection

HAVOC should attempt to detect whether a message is primarily English, Farsi, another supported language, or mixed-language text.

Use a local detection library or a lightweight heuristic where practical. Do not require an AI API for basic language identification.

Detection should consider:

- Persian/Arabic Unicode character ranges.
- English Latin characters.
- Text length and confidence.
- Mixed-language messages.
- Emojis and punctuation.
- Messages that contain too little text to classify reliably.

Do not misclassify every message containing one Persian character as Farsi. Use confidence thresholds and preserve the configured fallback when uncertain.

Localization architecture

All user-facing strings should be stored in a centralized localization system rather than scattered throughout feature code.

Provide:

- Translation dictionaries or structured locale files.
- Translation keys.
- English fallback for missing translations.
- Variable interpolation with validation.
- Pluralization support where needed.
- Consistent terminology across commands.
- A localization validation test that detects missing keys.
- Documentation explaining how to add another language later.

Avoid duplicating entire feature implementations for different languages. One implementation should support multiple locales.

Persian-specific requirements

- Correct Unicode handling.
- Right-to-left-friendly output.
- Proper display of Persian text beside English words, numbers, IDs, and URLs.
- Avoid corrupting punctuation or reversing text incorrectly.
- Use Persian-friendly date and number formatting where appropriate.
- Support Persian digits and standard Latin digits.
- Do not forcibly convert digits unless configured.
- Preserve original message text during translation or formatting.
- Test mixed text containing Persian, English, URLs, emojis, and code.

Language commands

Provide commands such as:

- ".lang"
- ".lang en"
- ".lang fa"
- ".lang auto"
- ".lang status"

Equivalent Persian command aliases or localized command descriptions should be available.

Example:

English:
"Language changed to English."

Farsi:
"زبان برنامه به فارسی تغییر کرد."

These are examples of intended behavior, not hard-coded output for every situation.

4. AUTOMATIC DETECTION AND CONTEXT ENGINE

HAVOC must proactively detect relevant events and information without turning into an uncontrolled automation engine.

Build a centralized detection pipeline. Features should subscribe to structured events instead of each module independently implementing overlapping message handlers.

Detection capabilities

HAVOC should be able to detect, when supported by available Telegram data:

- Incoming messages.
- Outgoing messages.
- Edited messages.
- Deleted-message events where Telegram actually exposes them.
- New private conversations.
- Group messages.
- Channel posts accessible to the account.
- Replies and reply chains.
- Mentions of the account.
- Direct replies to the account.
- Message forwarding metadata.
- Media and attachment types.
- Links and URLs.
- Telegram usernames and supported identifiers.
- Hashtags and command-like text.
- English and Farsi text.
- Mixed-language text.
- Keywords and configured phrases.
- Repeated messages and duplicate events.
- Potential message loops.
- Messages containing likely dates or times.
- Messages containing reminder-like requests.
- Potentially urgent messages based on configurable keywords.
- Configured notification keywords.
- Changes to accessible chat metadata.
- Scheduled-job deadlines.
- Scheduler failures.
- Network disconnects and reconnects.
- API rate-limit errors.
- Invalid configuration.
- Database errors.
- Feature-specific failures.
- Unusual bursts of events that could overload the application.

Do not claim that Telegram exposes data it does not provide. Deleted messages, read receipts, online status, edit history, and other events have API-specific limitations. Document those limitations.

Detection architecture

Every detected event should be normalized into an internal event object containing only the fields needed by subscribers, such as:

- Event type.
- Chat identifier.
- Sender identifier when available.
- Message identifier.
- Timestamp.
- Language estimate.
- Message type.
- Relevant text, only where required.
- Detection confidence.
- Correlation or deduplication identifier.

Keep sensitive information out of diagnostic logs.

The detection engine should support:

- Priorities.
- Event filtering.
- Per-feature subscriptions.
- Deduplication.
- Cooldowns.
- Per-chat configuration.
- Global feature switches.
- Error isolation.
- Debug mode.
- Metrics and diagnostics.
- Safe shutdown.

Detection must not automatically imply permission to act. For example, detecting a keyword may generate a notification, but it must not automatically send a message unless the corresponding feature is explicitly configured.

6. FEATURE CATALOGUE: 100 FEATURE AREAS

Implement these features as integrated modules. Some may share infrastructure, but each feature must have documented behavior, clear configuration, error handling, and appropriate tests.

A. Core infrastructure

1. Telegram account authentication

Implement Telethon login using API credentials, phone number, verification code, and 2FA when required. Support safe session reuse, session validation, recovery instructions, and graceful logout.

2. Modular command registry

Register commands with descriptions, categories, usage examples, aliases, localized help text, argument parsing, and feature ownership. Avoid a massive chain of conditionals.

3. Automatic language detection

Detect English, Farsi, mixed-language text, and uncertain input. Use confidence thresholds and a configurable fallback.

4. Complete localization system

Translate command responses, errors, help, notifications, status output, and setup guidance into English and Farsi.

5. Event detection engine

Normalize Telegram events into structured internal events and route them to interested modules.

6. Persistent settings

Store feature settings, language preferences, command prefix, cooldowns, and other preferences in SQLite.

7. Feature manager

Enable, disable, inspect, and configure features individually. Support a global emergency stop.

8. Persistent scheduler

Run delayed and recurring jobs with timezone support, stored execution state, retries where appropriate, and duplicate prevention.

9. Centralized rate limiter

Use configurable per-operation cooldowns and safe handling of Telegram FloodWait responses.

10. Health and diagnostics service

Track uptime, database health, active jobs, reconnects, recent sanitized errors, and feature status.

B. Profile and account customization

11. Live profile clock

".clock on/off/status" optionally updates the profile name with a configurable clock and timezone. Save and restore the original name. Use conservative intervals and default OFF.

12. Dynamic bio

Create rotating or scheduled bio text, with preview, enable, disable, and reset commands. Preserve the original bio when possible.

13. Profile presets

Save and apply named combinations of profile name, bio, and supported settings. List and delete presets, with confirmation before overwriting current values.

14. Profile scheduler

Schedule profile changes for specific times, weekdays, and timezones. Persist jobs across restarts.

15. Custom profile counters

Display configurable counters in supported profile fields, with increment, reset, and status commands. Validate limits and avoid excessively frequent profile edits.

16. Status rotation

Rotate among configured statuses, short descriptions, or profile presets according to a schedule.

17. Original profile restoration

Keep safe snapshots of profile values changed by HAVOC and provide a command to restore them.

18. Profile change history

Record the time and reason for profile changes initiated by HAVOC, without recording secrets.

19. Profile change safeguards

Prevent invalid lengths, repeated updates, accidental overwrites, and uncontrolled API requests.

20. Profile preview

Preview the proposed name, bio, or preset before applying it.

C. Messaging and communication

21. Smart auto-replies

Configure exact or keyword triggers, responses, per-chat rules, language preferences, cooldowns, and allow/deny lists. Prevent loops and ignore the account's own outgoing messages.

22. Away mode

Set an away message and optional reason. Support language-aware responses, exclusions, per-person cooldowns, and status commands.

23. Scheduled messages

Schedule one-time or recurring messages. List, cancel, and edit jobs where practical. Track execution state to prevent duplicates.

24. Message templates

Save reusable messages by name, preview them, edit them, and send them with validated placeholders such as "{name}", "{date}", and "{time}".

25. Contextual message suggestions

Offer draft replies based on the replied-to message, selected language, and configured tone. Never send automatically unless the user explicitly enables a safe, narrowly scoped rule.

26. Reply helper

Generate several concise response options for a replied-to message, such as friendly, formal, funny, supportive, or direct.

27. Fight Mode

".fight" on a replied-to message generates a contextual comeback. Include sarcastic, dry, clever, playful, dramatic, and blunt styles, configurable intensity, optional AI integration, and offline fallback templates. Show a preview before sending. Avoid threats, targeted slurs, private information, and genuinely dangerous harassment.

28. Language-aware replies

Choose English or Farsi based on the incoming message, chat preference, or configured default. Handle mixed-language input sensibly.

29. Reaction shortcuts

Configure phrase- or event-based reactions with cooldowns, chat scopes, duplicate prevention, and supported-reaction validation.

30. Message formatting toolkit

Format text as bold, italic, monospace, quotes, and spoilers where supported. Escape content correctly and preserve Persian text.

D. Detection and automation

31. Keyword notifications

Watch configured words or phrases and send private notifications to Saved Messages or another explicitly configured destination.

32. Mention detection

Detect accessible messages mentioning the account and optionally summarize or notify about them. Respect Telegram event availability.

33. Reply detection

Detect replies to the account and optionally notify, categorize, or prepare a draft response.

34. Message edit detection

Detect accessible edit events and optionally notify about changes. Do not promise access to complete historical versions.

35. Media-type detection

Recognize photos, videos, documents, audio, voice messages, stickers, animations, and other supported media.

36. Link detection

Extract URLs from accessible message text, identify repeated links, and support configurable link notifications. Never open suspicious links automatically.

37. Message language detection

Identify the likely language of messages and allow language-specific triggers, summaries, and notification rules.

38. Date and time detection

Recognize common date/time patterns in English and Farsi. Present a confirmation before turning ambiguous text into a scheduled job.

39. Reminder-intent detection

Recognize explicit reminder requests when configured. Ask for clarification through a draft or notification if the time or action is ambiguous; do not silently create surprising reminders.

40. Duplicate-event detection

Deduplicate repeated Telegram events and prevent automation loops. Keep bounded caches and persistent identifiers where necessary.

E. Search and information management

41. Message search

Search accessible message history by keyword and supported filters, with pagination and source context.

42. Chat search

Search accessible chats by name or username and show matching results without exposing inaccessible information.

43. Bookmark manager

Bookmark replied-to messages or notes. Support list, search, view, delete, and export/import.

44. Conversation notes

Maintain private notes associated with a chat. Notes must be clearly separate from Telegram messages and stored locally.

45. Contact and chat information

Show metadata available through Telegram, such as chat title, username, and relevant identifiers. Do not expose data that is not accessible.

46. Media information

Inspect a replied-to media item and display supported metadata such as type, size, filename, dimensions, or duration.

47. Explicit media downloader

Download media only when requested. Use safe filenames, configurable size limits, and path-traversal protection.

48. Export selected information

Export user-selected bookmarks, settings, notes, or other supported data to documented formats. Do not bulk-export private conversations by default.

49. Saved Messages assistant

Help organize notes, bookmarks, reminders, and personal messages in Saved Messages using explicit commands.

50. Search result summaries

Optionally summarize search results or selected text using a configured AI provider, with a non-AI fallback that simply presents matching excerpts.

51. Reminders

52. Recurring reminders

53. Timezone conversion

Display current times for configured cities or timezone names.

55. Scheduled task manager

58. Calendar-style overview

Display reminders and scheduled tasks for a selected day or week.

59. Quiet hours

Allow configurable hours when nonessential notifications and automatic replies should be paused.

60. Schedule validation

Detect invalid dates, past times, ambiguous timezone input, and recurrence conflicts before saving jobs.

G. Text, language, and AI utilities

61. Translation

Translate selected text or replied-to messages with a configurable provider. Keep provider credentials optional and explain offline limitations.

62. Translation preview

Show the original and translated text separately before replacing, forwarding, or sending anything.

64. Text cleanup

Normalize excessive whitespace, repeated punctuation, and other configurable formatting issues without silently changing meaning.

65. Text statistics

Calculate word, character, sentence, and line counts, including sensible handling of Persian text.

66. Text transformation

Provide configurable case conversion, text reversal, line sorting, deduplication, and other non-destructive transformations.

67. Jokes and quotes

Provide random jokes, short original quotes, and one-liners from an offline collection. Support English and Farsi entries.

68. Safe calculator

Evaluate basic arithmetic using a restricted parser, never Python "eval()". Validate expressions and reject unsafe syntax.

69. Random utilities

Generate random numbers, UUIDs, and other basic utility results with validated arguments.

70. AI provider abstraction

Support optional AI integrations through a common interface. Configure providers centrally, handle failures and timeouts, and allow offline fallback behavior. Never make core operation depend on paid AI access.

Define where automation is permitted or prohibited. Explicit denials should override broader allowlists.

77. Conversation categorization

78. Quick actions

Provide configurable shortcuts for commonly used commands, templates, bookmarks, and utilities.

79. Command aliases

Create, list, remove, and reset aliases. Prevent alias loops and reserved-command collisions.

80. Custom trigger rules

Define safe text/event patterns and actions. Provide test, list, enable, disable, and delete commands. Never execute arbitrary Python or shell commands from a rule.

81. Status dashboard

Show uptime, enabled features, pending jobs, database health, integrations, and recent sanitized errors.

82. Structured logging

Use rotating logs and configurable verbosity. Redact credentials, session strings, phone numbers where practical, and private message content.

83. Error reporting

Show useful, localized error messages and sanitized diagnostic details. Keep full stack traces in protected local logs when appropriate.

84. Crash recovery

Handle reconnects, network errors, shutdown, and database failures with bounded retries and backoff.

Track schema versions and apply migrations safely without silently destroying existing data.

87. Configuration validator

Check required values, invalid settings, unsupported options, missing integrations, and conflicting feature configuration at startup.

88. Plugin loader

Load trusted local Python plugins through a documented interface. Validate plugin metadata, isolate failures, and never download and execute arbitrary code.

89. Performance diagnostics

Measure event-processing latency, queue sizes, database response time, scheduler delays, and memory use where practical. Avoid high-frequency polling.

90. Graceful shutdown and recovery

Stop accepting new work, finish or cancel safe pending tasks, close database connections, and release client resources correctly.

92. Feature usage statistics

Track local counts such as command invocations, successful jobs, failures, and processing latency. Avoid collecting unnecessary personal data.

98. Backup scheduling

99. Developer extension API

Document how developers can add commands, event subscribers, localized strings, database migrations, and feature settings without modifying unrelated modules.

100. Self-check and update readiness

- Keep automatic replies, away mode, profile changes, and trigger rules OFF until configured.
- Use allowlists, cooldowns, a global stop switch, and dry-run mode.
- Do not bypass access restrictions or claim access to inaccessible Telegram data.
- Do not run untrusted plugin code.
- Validate file paths and import data.
- Protect backups containing private information.
- Provide clear uninstall and data-deletion instructions.
- No hidden telemetry.
